[2] DB / REDIS / STORAGE ARCHITECTURE

발표 문장:
데이터 계층 아키텍처입니다. 데이터 요청 시 DB Pod에 직접 접근하지 않고 ProxySQL Service를 통해 PXC로 접근합니다.
예매 상태처럼 여러 앱이 동일한 기준으로 사용해야 하는 상태 정보는 Redis 계층에서 조회할 수 있도록 구성했습니다.
Storage는 역할에 따라 block storage와 object storage로 분리했습니다.

참고:
- Redis Sentinel: HA/failover 목적, 강한 일관성 보장 구조로 설명 금지
- AWS burst app: 예매 상태는 Redis, 예매 외 read-only 데이터는 AWS read-only DB 계층

[3] BACKUP ARCHITECTURE

발표 문장:
조금 더 자세한 구조를 보면 Kubernetes PVC 데이터들은 RBD Pool 기반으로 구성했고, Harbor 이미지 와 이미지·영상파일과 같은 app object 들은 RGW/S3 기반으로 구성했습니다.
RGW/S3의 데이터는 설정된 주기마다 AWS S3로 backup 되도록 적용했고, 구조도에는 없지만 etcd 데이터도 S3로 backup 되도록 했습니다. Harbor 이미지는 AWS로 burst할 때 이미지를 빠르게 pull할 수 있도록 ECR로 미러링되도록 설정했습니다.

참고:
- etcd snapshot: Kubernetes control plane 복구 목적, application DB backup 아님
- 추가 대상: Harbor metadata, PXC DB data

---

[4] WHY THESE TECHNOLOGIES?

발표 문장:
이어서, 각 기술 스택을 선택한 이유를 설명드리겠습니다.
Ceph는 하나의 storage backend에서 RBD와 RGW를 모두 제공할 수 있어서 선택했습니다.
PXC는 여러 DB Pod로 구성해, 일부 Pod 장애에도 DB 서비스를 유지하기 위해 사용했습니다.
ProxySQL은 애플리케이션이 여러 DB Pod를 직접 바라보지 않도록 DB endpoint를 단순화하고, writer routing과 connection 관리를 통해 DB 접근을 안정적으로 제어하기 위해 사용했습니다.
Redis는 DB 부하를 줄이고, 온프레미스와 AWS burst app이 동일한 예매 상태를 공유하도록 하기 위해 사용했습니다.

참고:
- Redis Sentinel은 failover 구조
- Redis를 강한 일관성 저장소처럼 표현 금지

---

[5] RBD + RGW ACTUAL USE

발표 문장:
RBD, RGW, Redis가 어떻게 사용되고 있는지 좀 더 구체적으로 말씀드리겠습니다.
RBD는 Kubernetes PVC와 VM disk처럼 block volume이 필요한 영역에 사용했습니다.
PXC DB volume, Redis volume, Harbor metadata, Jenkins, Prometheus, Grafana, Proxmox VM disk가 여기에 해당합니다.
RGW/S3는 Harbor image blob과 앱의 이미지, 영상 object 저장에 사용했습니다.
Redis는 앞서 말씀드린바와 같이 예매 상태 공유, 부하 감소를 담당하고,
Redis Sentinel은 Redis 장애 감지와 자동 failover를 담당합니다.

참고:
- ProxySQL: DB data 저장 계층 아님, endpoint/routing 계층
- Harbor image blob: registry layer와 manifest 저장 구조를 고려한 표현

- Harbor image mirror: backup과 별도 목적

[7] BACKUP POLICY

발표 문장:
Replica가 디스크/노드 장애에 대비한 가용성 확보 수단이라면, Backup은 데이터 삭제나 오염 발생 시 복구하기 위한 보호 수단입니다.
Backup 정책은 현재 적용된 범위와 보강할 범위를 나눠서 설명하겠습니다.
현재는 etcd와 S3 object backup이 적용되어 있고, Harbor metadata와 PXC DB data는 추가 적용 대상입니다.
추후에는 backup 절차의 정상 동작 확인뿐만 아니라, 특정 시점으로 실제 복구 가능한지까지 검증해야 합니다.

참고:
- 검증 기준: backup success, restore success, checksum, recovery log
- 운영 기준: RPO, RTO, retention 정의 필요

[8] PERFORMANCE EVIDENCE

발표 문장:
Ceph는 10G network로 연결되어 있기 때문에 처음에는 storage 성능도 충분히 나올 것으로 예상했습니다.
하지만 RBD PVC 기준 fio 테스트에서 write 성능이 낮게 나와, network 성능부터 확인했습니다.
먼저 10G Network Check에서 Ceph node 간 전송 속도가 정상 범위인지 확인했습니다.
캡처의 `9.99 Gbits/sec receiver`는 10G 대역폭이 거의 정상적으로 나온 근거입니다.
따라서 병목 후보는 network보다는 HDD OSD와 replica write가 포함된 RBD write path 쪽으로 좁혀졌습니다.
4K random write는 DB 저장 작업과 유사한 write 패턴이고, 1M sequential write는 큰 파일 연속 write 패턴입니다.
`write` 줄은 처리량, `clat percentiles`는 write 지연 시간 분포, `Disk stats util`은 RBD 장치가 얼마나 바빴는지 보여줍니다.
Disk util이 99~100%인 것을 통해 테스트 중 RBD write path가 거의 계속 바빴다는 근거로 볼 수 있습니다.

참고:
- 10G Network Check: `9.99 Gbits/sec receiver`, 10G 링크 정상 범위
- 4K random write: 작은 DB성 write 패턴
- 1M sequential write: 큰 파일 연속 write 패턴
- p95 latency 근거: fio `clat percentiles`의 `95.00th`
- `usec` 단위는 1000으로 나누면 ms 기준
- 표현 기준: 현재 RBD PVC 단일 write 테스트

---

[9] PERFORMANCE ANALYSIS

발표 문장:
확인 결과를 다시 확인하면 Network는 9.99 Gbits/sec로 10G 정상 범위에 가깝게 확인됐고, RBD write는 기대보다 낮게 나왔습니다.
따라서 전송선 자체가 병목일 가능성은 낮고, storage write path 중심으로 봐야 한다는 것입니다.
현재 ceph 구성은 HDD OSD와 replica write를 거치는 RBD write path 영향을 받습니다.
그래서 결론은 network는 정상 범위이고, 병목 후보는 HDD OSD와 replica write 기반 RBD write path라는 것입니다.
개선 방안은 WAL/DB를 SSD로 분리하거나, 운영급에서는 NVMe OSD 전환까지 검토하는 방향입니다.

참고:
- 금지 표현: "10G라서 Ceph도 빠름"
- 권장 표현: "10G network와 Ceph write path는 별도 검증 대상"
- PPT의 `원인`은 확정 원인보다 `병목 후보` 의미로 설명
- 현재 측정 기준: Kubernetes RBD PVC 단일 write 테스트

[10] CURRENT LIMITATIONS

발표 문장:
현재 구조에서 개선해야할 부분은 네 가지입니다.
먼저 HDD 기반 RBD write path는 운영급 성능 개선 검토가 필요합니다.
Harbor metadata와 PXC DB data backup 을 추가로 적용해야하고,
특정 버전의 backup으로 실제 복구하는 절차 검증이 필요합니다.
넷째, RPO·RTO·백업 보관 기간 등 복구 기준에 대한 구체적인 수치 정의가 필요합니다.

여기까지 데이터 layer 설계와 성능 검증이었습니다. 다음으로 이 위에서 코드가 어떻게 배포되는지 CI/CD 담당 강재형님이 이어가겠습니다.
