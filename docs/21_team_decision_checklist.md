# Team Decision Checklist

팀 회의에서 함께 결정해야 하는 아키텍처 선택지와 용어 설명

---

## 1. 이 문서의 목적

이 프로젝트는 온프레미스(Proxmox)와 AWS를 함께 사용하는 하이브리드 인프라를 목표로 함. 다만 “함께
사용한다”는 말 안에도 여러 방식이 있음.

2026-05-07 기준 MVP는 아래 방향으로 고정함.

| 결정 항목         | MVP 선택                                      | 확장 또는 비교안                                      |
| :---------------- | :-------------------------------------------- | :---------------------------------------------------- |
| 클러스터 구성     | 온프레미스 Kubernetes와 AWS burst 별도 런타임 | EKS 최소 PoC, EKS Hybrid Nodes                        |
| 웹앱 실행 위치    | 온프레미스 기본, AWS는 EC2 ASG/ALB burst      | 온프레미스/AWS 상시 병행                              |
| DB 위치           | AWS EC2 기반 PXC/ProxySQL MVP                 | 온프레미스 DB, 양쪽 분산 DB                           |
| 파일/백업 저장소  | Ceph RGW 우선                                 | AWS S3 2차 복제                                       |
| EKS 사용 여부     | 최소 PoC 포함                                 | 운영용 EKS 전환, 비용/운영 편의성 비교                |
| AWS EC2 확장 방식 | 일반 앱 서버 ASG                              | EC2 직접 Kubernetes 구성은 제외                       |
| 트래픽 분산       | DNS 또는 발표용 수동 endpoint 전환            | 자동 failover, Route 53 고급 정책                     |
| GitOps 정책       | Day 13 전 수동 sync 기본                      | 안정화 후 auto-sync/self-heal                         |
| 비용 제한         | ASG 낮은 Max, 단일 NAT, 발표 후 삭제          | 고가용 NAT, ProxySQL 이중화, HTTPS, PMM, Loki 등 확장 |

예를 들어 다음 질문들은 모두 팀이 명확히 합의해야 함.

- 온프레미스와 AWS를 하나의 Kubernetes 클러스터로 묶을 것인가?
- 아니면 온프레미스 Kubernetes와 AWS EC2 Auto Scaling을 별도 런타임으로 둘 것인가?
- 웹앱과 DB를 모두 온프레미스에서 실행하고, 부하가 높을 때만 AWS로 확장할 것인가?
- 파일 저장소는 AWS S3를 쓸 것인가, 온프레미스 Ceph RGW를 쓸 것인가?
- EKS를 MVP 최소 PoC로 어디까지 수행하고, 운영 전환은 어디까지 제외할 것인가?

이 문서는 위 질문을 기술을 잘 모르는 팀원도 이해할 수 있도록 풀어서 정리하고, 회의에서 선택할 수
있는 결정지를 제공함.

## 2. 먼저 알아야 할 용어

| 용어                    | 쉽게 말하면                                                    | 이 프로젝트에서의 의미                        |
| :---------------------- | :------------------------------------------------------------- | :-------------------------------------------- |
| 온프레미스(On-premises) | 직접 소유하거나 직접 관리하는 서버 환경                        | Proxmox 장비와 그 위의 VM, Kubernetes, Ceph   |
| Proxmox                 | 서버 한 대 또는 여러 대에서 VM을 만들고 관리하는 가상화 플랫폼 | 온프레미스 VM과 Ceph 운영 기반                |
| Kubernetes(K8s)         | 여러 서버 위에 컨테이너 앱을 배포하고 자동 복구하는 플랫폼     | 온프레미스 앱 실행의 중심 후보                |
| Cluster                 | 여러 서버를 하나의 묶음처럼 관리하는 단위                      | Kubernetes 클러스터 또는 DB 클러스터          |
| Node                    | 클러스터에 참여하는 서버 또는 VM                               | Kubernetes worker node, AWS EC2 node 등       |
| Pod                     | Kubernetes에서 앱 컨테이너가 실행되는 가장 작은 단위           | 웹앱 컨테이너 실행 단위                       |
| Ingress                 | Kubernetes 내부 앱을 외부에서 접근 가능하게 하는 입구          | 온프레미스 웹앱 진입점                        |
| EC2                     | AWS에서 빌려 쓰는 가상 서버                                    | 부하 증가 시 추가 실행되는 burst 서버         |
| ALB                     | HTTP/HTTPS 요청을 여러 서버로 나누어 보내는 AWS 로드밸런서     | AWS burst 영역의 외부 진입점                  |
| Auto Scaling Group(ASG) | 조건에 따라 EC2를 자동으로 늘리거나 줄이는 AWS 기능            | 부하 증가 시 AWS EC2 생성, 부하 감소 시 종료  |
| Launch Template         | 새 EC2를 만들 때 사용할 서버 설정 템플릿                       | AMI, 인스턴스 타입, user data, 보안그룹 정의  |
| CloudWatch              | AWS 로그, 지표, 알람 서비스                                    | CPU, 요청 수, 장애 감지와 scale-out 기준      |
| ECS                     | AWS의 컨테이너 실행 서비스                                     | 기존 fallback 구조. Kubernetes는 아님         |
| Fargate                 | 서버를 직접 관리하지 않고 컨테이너만 실행하는 AWS 방식         | ECS fallback에서 사용 가능                    |
| EKS                     | AWS가 관리해주는 Kubernetes 서비스                             | 비용과 관리 편의성 사이의 선택지              |
| EKS Hybrid Nodes        | 온프레미스 서버를 EKS 클러스터 노드처럼 붙이는 AWS 기능        | 정석적인 hybrid Kubernetes 후보지만 비용 증가 |
| S3                      | AWS 객체 저장소 서비스                                         | 파일, 백업, 정적 자산 저장 후보               |
| Ceph                    | 직접 운영하는 분산 스토리지                                    | 온프레미스 저장소                             |
| Ceph RGW                | Ceph를 S3처럼 사용할 수 있게 해주는 게이트웨이                 | 온프레미스 S3 호환 저장소                     |
| RBD                     | Ceph의 블록 스토리지                                           | Proxmox VM 디스크, Kubernetes PV 후보         |
| CephFS                  | Ceph의 공유 파일 시스템                                        | 여러 노드가 공유하는 파일 저장 후보           |
| PXC                     | MySQL 호환 DB를 여러 노드로 묶는 Percona DB 클러스터           | RDS 대신 직접 운영하는 DB 후보                |
| ProxySQL                | 앱과 DB 사이에서 DB 접속을 중계하는 프록시                     | 앱은 DB 노드가 아니라 ProxySQL로 접속         |

## 3. 결정 1: 온프레미스와 AWS를 하나의 클러스터로 묶을 것인가?

### 질문

온프레미스 서버와 AWS EC2를 **하나의 Kubernetes 클러스터**로 만들 것인가, 아니면 **서로 다른 실행
환경**으로 둘 것인가?

### 선택지

| 선택지          | 설명                                                      | 장점                             | 단점                                               |
| :-------------- | :-------------------------------------------------------- | :------------------------------- | :------------------------------------------------- |
| A. 별도 런타임  | 온프레미스는 K8s, AWS는 EC2 ASG/ALB로 따로 운영           | 비용이 낮고 구현이 현실적임      | 단일 K8s 클러스터는 아니므로 설명을 명확히 해야 함 |
| B. EKS 최소 PoC | AWS 관리형 Kubernetes를 짧게 생성/배포/삭제 검증          | EKS 경험과 비교 근거 확보 가능   | 운영 MVP로 쓰면 비용과 일정 부담 증가              |
| C. EKS Hybrid   | AWS EKS가 control plane을 관리하고 온프레미스 node를 붙임 | 관리 부담이 낮고 구조가 정석적임 | EKS 비용과 네트워크 준비 부담이 큼                 |

### 현재 추천

**B. 별도 런타임**을 MVP로 권장함.

이유:

- 비용 우선 조건과 가장 잘 맞음
- EKS control plane 비용을 피할 수 있음
- 팀이 AWS에서 실습한 CloudWatch + ASG + ALB 흐름을 재사용 가능
- 13일 구축 일정에서 성공 가능성이 높음

### 회의에서 결정할 것

- [ ] MVP는 별도 런타임으로 간다
- [ ] 단일 Kubernetes 클러스터 확장은 이번 범위에서 제외한다
- [ ] EKS 최소 PoC와 EKS Hybrid는 발표의 비교/향후 과제로 설명한다

## 4. 결정 2: 웹앱은 어디에서 기본 실행할 것인가?

### 질문

평소 웹앱을 온프레미스에서 실행하고 AWS는 부하가 높을 때만 쓸 것인가, 아니면 AWS에서도 항상 일부
앱을 실행할 것인가?

### 선택지

| 선택지                          | 설명                                                | 장점                      | 단점                                |
| :------------------------------ | :-------------------------------------------------- | :------------------------ | :---------------------------------- |
| A. 온프레미스 기본, AWS는 burst | 평소에는 Proxmox K8s에서 운영, 부하 때 AWS EC2 추가 | 비용 절감 메시지가 명확함 | 트래픽 분산과 배포 버전 동기화 필요 |
| B. 온프레미스와 AWS 상시 병행   | 양쪽에 항상 앱을 띄움                               | 장애 대비 설명이 쉬움     | AWS 비용이 계속 발생                |
| C. AWS 기본, 온프레미스 보조    | 클라우드 중심 운영                                  | AWS 서비스 활용은 쉬움    | 온프레미스 구축 의미가 약해짐       |

### 현재 추천

**A. 온프레미스 기본, AWS는 burst**를 권장함.

AWS burst EC2는 가능한 한 상태 없는(stateless) 웹앱만 실행하는 것이 좋음. 사용자가 업로드한 파일,
세션, DB 데이터처럼 사라지면 안 되는 데이터는 별도 저장소에 둬야 함.

### 회의에서 결정할 것

- [ ] 평소 트래픽은 온프레미스 Kubernetes가 처리한다
- [ ] AWS EC2는 부하 증가 시에만 추가한다
- [ ] AWS EC2는 상태 없는 앱 실행 영역으로 제한한다
- [ ] 온프레미스 장애 시 AWS를 임시 주 실행 환경으로 사용할지 결정한다

## 5. 결정 3: DB는 어디에 둘 것인가?

### 질문

DB를 온프레미스에 둘 것인가, AWS EC2에 둘 것인가, 양쪽에 나눌 것인가?

### 선택지

| 선택지           | 설명                              | 장점                                        | 단점                                              |
| :--------------- | :-------------------------------- | :------------------------------------------ | :------------------------------------------------ |
| A. DB 온프레미스 | PXC/ProxySQL을 Proxmox VM에 구성  | AWS DB 비용 절감, 온프레미스 운영 경험 확보 | AWS burst 앱이 DB에 접근하려면 네트워크 연결 필요 |
| B. DB AWS EC2    | PXC/ProxySQL을 AWS EC2에 구성     | AWS burst 앱과 연결이 쉬움                  | EC2 비용이 계속 발생                              |
| C. DB 양쪽 분산  | 온프레미스와 AWS에 DB 노드를 나눔 | 하이브리드 느낌이 강함                      | 지연 시간, 장애 처리, 데이터 정합성 설명이 어려움 |

### 현재 추천

비용 우선이면 **A. DB 온프레미스**를 먼저 검토함. 다만 발표 안정성이 더 중요하면 **B. DB AWS EC2**가
더 단순함.

PXC는 노드 간 통신이 많기 때문에 온프레미스와 AWS에 노드를 섞어 배치하면 네트워크 지연 때문에 운영
난이도가 크게 올라갈 수 있음. 13일 MVP에서는 DB 노드를 양쪽에 나누는 구조는 권장하지 않음.

### 회의에서 결정할 것

- [ ] DB는 온프레미스에 둘지 AWS EC2에 둘지 결정한다
- [ ] AWS burst 앱이 ProxySQL에 접근하는 네트워크 경로를 결정한다
- [ ] PXC 노드를 온프레미스/AWS에 섞어 배치하지 않는다는 원칙에 합의한다
- [ ] ProxySQL 1대 MVP와 2대 이중화 중 어디까지 할지 결정한다

## 6. 결정 4: 파일 저장소는 AWS S3인가, 온프레미스 S3 호환 저장소인가?

### 질문

앱 파일, 백업 파일, 정적 파일을 어디에 저장할 것인가?

### 선택지

| 선택지                    | 설명                                        | 장점                                    | 단점                                   |
| :------------------------ | :------------------------------------------ | :-------------------------------------- | :------------------------------------- |
| A. AWS S3                 | AWS 관리형 객체 저장소 사용                 | 안정성 높고 연동 쉬움                   | AWS 비용 발생                          |
| B. Ceph RGW               | 온프레미스 Ceph를 S3처럼 사용               | AWS 저장 비용 절감, 직접 운영 경험 확보 | RGW 구성과 보안, 백업 책임이 팀에 있음 |
| C. Ceph RGW + AWS S3 복제 | 기본은 온프레미스, 중요 데이터만 AWS에 복제 | 비용과 안정성 균형                      | 구현 범위가 늘어남                     |

### 현재 추천

**B. Ceph RGW 우선, C는 선택 확장**을 권장함.

### 온프레미스 저장소를 S3처럼 쓰려면 필요한 것

Ceph RGW를 사용하면 앱 입장에서는 AWS S3와 비슷한 방식으로 파일을 저장할 수 있음. 단, 다음 구성이
필요함.

| 필요한 것               | 설명                                                     |
| :---------------------- | :------------------------------------------------------- |
| Ceph cluster            | 데이터를 실제로 저장하는 온프레미스 분산 스토리지        |
| RGW daemon              | S3 호환 HTTP API를 제공하는 구성 요소                    |
| Bucket                  | 파일을 담는 논리 공간. AWS S3 bucket과 비슷함            |
| Access Key / Secret Key | 앱이 RGW에 접근할 때 쓰는 인증 정보                      |
| HTTPS endpoint          | 앱이 안전하게 접근할 수 있는 RGW 주소                    |
| 접근 제한               | 인터넷 전체 공개 금지. VPN, 제한된 IP, 방화벽, 인증 적용 |
| 백업 정책               | RGW에 저장된 데이터를 어떻게 보호할지 결정               |

### 회의에서 결정할 것

- [ ] 앱 파일 저장소는 Ceph RGW를 우선 사용한다
- [ ] DB 백업 저장소도 Ceph RGW를 우선 사용한다
- [ ] 중요한 백업만 AWS S3로 2차 복제할지 결정한다
- [ ] RGW endpoint를 VPN 안에서만 열지, 제한된 HTTPS로 열지 결정한다
- [ ] RGW Access Key를 어디에 저장할지 결정한다

## 7. 결정 5: EKS를 사용할 것인가?

### 질문

AWS 관리형 Kubernetes 경험을 MVP에 넣을 것인가, 아니면 별도 PoC/비교안으로 둘 것인가?

### 선택지

| 선택지                   | 설명                                                 | 장점                              | 단점                                      |
| :----------------------- | :--------------------------------------------------- | :-------------------------------- | :---------------------------------------- |
| A. 온프레미스 Kubernetes | Proxmox VM에 kubeadm, k3s, RKE2 등으로 직접 구성     | 비용 낮음, 직접 운영 학습 효과 큼 | 설치, 업그레이드, 장애 대응을 직접 책임짐 |
| B. EKS 최소 PoC          | AWS가 관리하는 Kubernetes를 짧게 생성/배포/삭제 검증 | EKS 경험과 비교 근거 확보 가능    | 운영 경로로 쓰면 비용과 일정 부담 증가    |
| C. 운영용 EKS 전환       | AWS EKS를 실제 운영 Kubernetes 런타임으로 사용       | AWS 관리형 기능 활용 가능         | MVP 범위와 비용이 커짐                    |
| D. EKS Hybrid Nodes      | 온프레미스 node를 EKS 클러스터에 붙임                | 하이브리드 K8s 구조가 깔끔함      | 비용과 네트워크 준비 부담                 |

### 현재 추천

**온프레미스 Kubernetes를 운영 MVP로 유지하고, EKS 최소 PoC를 MVP 보조 산출물로 포함**함.

EKS는 좋은 서비스이고 사용 경험도 의미가 있으므로 클러스터 생성, `kubectl` 연결, 샘플 앱 배포, 삭제
검증까지는 수행함. 다만 지금 프로젝트의 우선순위가 비용 절감과 13일 내 발표 안정성이므로 운영용 EKS
전환은 제외하는 편이 좋음.

### 회의에서 결정할 것

- [ ] MVP에서는 EKS 최소 PoC를 수행한다
- [ ] 운영용 EKS 전환은 사용하지 않는다
- [ ] AWS Load Balancer Controller, EKS Hybrid Nodes, 운영용 EKS 전환은 향후 확장안으로 둔다

## 8. 결정 6: AWS EC2 확장은 어떤 방식인가?

### 질문

부하가 높아질 때 생성되는 AWS EC2를 어떻게 사용할 것인가?

### 선택지

| 선택지               | 설명                                                | 장점                         | 단점                        |
| :------------------- | :-------------------------------------------------- | :--------------------------- | :-------------------------- |
| A. 일반 앱 서버 확장 | EC2가 user data로 앱 컨테이너를 실행하고 ALB에 붙음 | 구현이 쉽고 비용 제어가 쉬움 | Kubernetes node 확장은 아님 |

### 현재 추천

**A. 일반 앱 서버 확장**을 MVP로 권장함.

AWS EC2에 직접 Kubernetes를 설치해 온프레미스 클러스터의 worker로 붙이는 구성은 이번 MVP와 선택 확장
범위에서 제외함. 발표에서는 “Kubernetes cloud bursting”이라고 표현하기보다 “온프레미스 Kubernetes
기본 운영 + AWS EC2 Auto Scaling burst”라고 표현해야 정확함.

### 회의에서 결정할 것

- [ ] AWS EC2 burst는 일반 앱 서버 확장으로 구현한다
- [ ] AWS EC2 직접 Kubernetes 구성은 이번 범위에서 제외한다
- [ ] 발표 표현에서 단일 Kubernetes cluster라고 과장하지 않는다

### 아직 결정되지 않은 논의 사항: 온프레미스 CPU 기준 EKS 확장

온프레미스 Kubernetes의 CPU 사용량이 일정 기준을 초과했을 때 EKS로 확장하는 구조는 아직 확정하지
않음.

현재 판단:

- EKS는 AWS 쪽 Kubernetes 실행 환경을 관리형으로 제공하지만, 온프레미스 부하를 자동 감지해 EKS로
  확장하는 전체 흐름을 기본으로 제공하지는 않음
- 자동화하려면 온프레미스 Prometheus/Alertmanager, Webhook 또는 Lambda/GitHub Actions, EKS
  Deployment scale-out, Route 53 또는 ALB 기반 트래픽 전환 설계가 추가로 필요함
- MVP에서는 AWS EC2 ASG/ALB burst를 우선 구현하고, EKS는 동일 앱 배포 검증 또는 관리형 Kubernetes
  최소 PoC로 제한하는 편이 안전함

논의할 선택지:

| 선택지                                                   | 설명                                                                             | 판단          |
| :------------------------------------------------------- | :------------------------------------------------------------------------------- | :------------ |
| A. 온프레미스 부하 증가 시 AWS EC2 ASG/ALB 사용          | 현재 MVP 방향. CloudWatch/ASG/ALB 기준으로 AWS burst를 설명                      | 우선 구현     |
| B. 같은 이미지를 EKS에도 배포                            | EKS를 AWS 관리형 Kubernetes 배포 검증 환경으로 사용                              | 최소 PoC 후보 |
| C. 온프레미스 Alert → EKS scale-out → 트래픽 전환 자동화 | Prometheus Alertmanager, Lambda 또는 GitHub Actions, EKS 권한, DNS/ALB 전환 필요 | 향후 논의     |

회의에서 결정할 것:

- [ ] EKS PoC를 단순 샘플 앱 배포로 둘지, 실제 앱 동일 이미지 배포까지 할지 결정한다
- [ ] 온프레미스 CPU 임계치 기반 EKS scale-out 자동화는 향후 확장으로 둘지 결정한다
- [ ] EKS endpoint를 발표에서 실제 접속 확인 대상으로 보여줄지, 캡처/비교표로만 둘지 결정한다

## 9. 결정 7: 트래픽은 어떻게 나눌 것인가?

## 11. 결정 9: 세션과 업로드 파일은 어디에 저장할 것인가?

### 질문

AWS burst EC2가 생겼다 사라져도 사용자의 로그인 상태나 업로드 파일이 사라지지 않게 하려면 어떻게 할
것인가?

### 선택지

| 데이터      | 권장 위치                        | 이유                                                 |
| :---------- | :------------------------------- | :--------------------------------------------------- |
| 세션        | DB 또는 Redis 같은 외부 저장소   | EC2가 종료되어도 세션 유지 가능                      |
| 업로드 파일 | Ceph RGW 또는 AWS S3             | 앱 서버 디스크에 저장하면 scale-in 때 사라질 수 있음 |
| 로그        | CloudWatch 또는 중앙 로그 저장소 | 장애 분석과 발표 캡처에 필요                         |
| DB 데이터   | PXC                              | 앱 서버와 분리해야 함                                |

### 현재 추천

AWS burst EC2는 상태 없는 앱 서버로 두고, 파일과 세션은 외부 저장소에 둠.

### 회의에서 결정할 것

- [ ] 앱 서버 로컬 디스크에 중요한 데이터를 저장하지 않는다
- [ ] 업로드 파일은 Ceph RGW 또는 AWS S3 중 하나로 정한다
- [ ] 세션이 필요한 앱이면 세션 저장 위치를 정한다
