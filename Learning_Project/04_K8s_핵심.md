## 1) K8s가 풀어주는 문제

```
[Docker 컨테이너 100개를 어떻게 운영?]

수동:
- 어느 서버에 어떤 컨테이너 배치할지?
- 컨테이너 죽으면 누가 살리나?
- 트래픽을 어떻게 분산하나?
- 새 버전 배포 무중단?
- 자원 부족 시 어디로 옮기나?

→ K8s가 다 자동화
```

## 2) 아키텍처

```
┌────────────────────────────────────────────┐
│ Control Plane (대뇌)                        │
│  ┌──────────┐ ┌──────────┐                 │
│  │ API      │ │ etcd     │ 상태 저장        │
│  │ Server   │ │ (3대)    │                 │
│  └──────────┘ └──────────┘                 │
│  ┌──────────┐ ┌──────────┐                 │
│  │Scheduler │ │Controller│ 자동화 룹        │
│  └──────────┘ └──────────┘                 │
└────────────────────────────────────────────┘
         ↕ kube-proxy (네트워크)
┌────────────────────────────────────────────┐
│ Worker Node                                 │
│  ┌──────────┐ ┌──────────┐                 │
│  │ kubelet  │ │containerd│                 │
│  └──────────┘ └──────────┘                 │
│      [Pod] [Pod] [Pod] ...                  │
└────────────────────────────────────────────┘
```

| 컴포넌트           | 역할                                    |
| ------------------ | --------------------------------------- |
| API Server         | 모든 명령의 진입점 (REST API)           |
| etcd               | 클러스터 상태 저장 (분산 KV store)      |
| Scheduler          | Pod을 어느 노드에 배치할지 결정         |
| Controller Manager | 원하는 상태로 자동 맞춤 (ReplicaSet 등) |
| kubelet            | 노드에서 Pod 실행/관리                  |
| containerd         | 컨테이너 런타임 (Docker 아님)           |
| kube-proxy         | iptables/IPVS로 Service 라우팅          |
| CNI plugin         | Pod 네트워크 (Calico)                   |

---

## 3) 왜 etcd는 홀수 (3, 5, 7)?

분산 합의 알고리즘 Raft는 **과반수**가 필요. 3대 → 2대 살아있으면 OK. 4대 → 3대 필요 (4대 중 2대
죽으면 안 됨, 차라리 3대가 나음).

3-CP가 최소 HA. 우리도 3대 (cp1, cp2, cp3).

## 4) 워크로드 타입

| 타입              | 용도                      | 우리 예시               |
| ----------------- | ------------------------- | ----------------------- |
| **Pod**           | 최소 단위 (컨테이너 1+개) | (직접 X)                |
| **Deployment**    | 상태 없는 앱 (Stateless)  | FastAPI 앱              |
| **StatefulSet**   | 상태 있는 앱              | (Operator가 사용)       |
| **DaemonSet**     | 모든 노드에 1개씩         | Calico, MetalLB speaker |
| **Job / CronJob** | 일회성 / 정기 작업        | 백업, 마이그레이션      |

## 5) kubeadm vs 대안

| 방법        | 특징                           | 우리 선택   |
| ----------- | ------------------------------ | ----------- |
| **kubeadm** | 공식 표준, 수동/Ansible로 구성 | ✅          |
| kubespray   | Ansible 자동화 (복잡)          | -           |
| k3s         | 경량, 단일 바이너리            | 학습 가치 ↓ |
| OpenShift   | 상용, RBAC 강력                | 학습 부담 ↑ |
| Rancher     | UI 제공, 멀티 클러스터         | -           |

kubeadm을 직접 다루면 K8s 동작 원리 깊이 이해.

## 7) Pod 네트워크 흐름

```
[Pod A on Node 1] (10.244.1.5)
    ↓ Service ClusterIP (10.96.X.Y)
[kube-proxy: iptables/IPVS]
    ↓
[Pod B on Node 2] (10.244.2.7)
    ↓ 응답
```

Calico가 노드 간 VXLAN tunnel로 Pod CIDR 라우팅.

## 8) 발표 어필

> _"K8s Control Plane을 3대로 HA 구성하여 etcd quorum을 유지합니다. 단일 CP 다운에도 클러스터 운영이
> 지속되며, 워커 노드도 3개 다른 Proxmox 호스트에 분산되어 단일 PVE 장애 시 최대 1대만 손실됩니다."_
