# 01. 물리 인프라 + 네트워크 설계

> ⭐ **한 줄 요약**: Proxmox 4대와 Ceph 6대를 **물리적으로 분리**해 컴퓨트와 스토리지의 장애가 서로에게 번지지 않도록 했다. 그 위에 **10G Spine-Leaf 패브릭**을 깔아 Ceph replication과 K8s Pod 간 통신이 1G에서 병목되지 않게 했다. **pfSense HA**가 VLAN 4개의 게이트웨이 + 방화벽 + DNS를 통합 담당한다.

---

## 🎯 우리가 한 선택

### 물리 장비

전체 인프라는 크게 컴퓨트 4대, 스토리지 6대, 네트워크 장비 10대로 구성된다. 학습 환경치고는 적지 않은 규모인데, 이렇게 한 이유는 진짜 production-grade 패턴 (장애 격리, 분산, HA)을 직접 경험해보기 위해서다. 작은 환경에서 단순화하면 실제 운영에서 발생하는 문제들을 미리 마주칠 기회가 없다.

| 장비 | 수량 | 사양 | 역할 |
|---|---|---|---|
| **Proxmox 노드** | 4 | LG B80LV (i7-13700, 16C/24T, 32GB RAM) | VM 호스트 (K8s, pfSense, bastion 등) |
| **Ceph 노드** | 6 | 별도 어플라이언스 (1TB HDD, BlueStore) | 분산 스토리지 (RBD/RGW) |
| **JT-S508CL-8S Spine** | 2 | 10G 8포트 | Leaf 간 백본 |
| **JT-S508CL-8S Leaf** | 5 | 10G 8포트 | 노드 직접 연결 |
| **관리 스위치** | 1 | 1GbE | Proxmox + 노트북 |

Proxmox 노드 한 대당 i7-13700에 32GB RAM은 학습 환경에 충분한 사양이다. 16 코어 / 24 스레드라 VM 여러 대 띄워도 CPU는 여유가 있다. 다만 메모리 32GB는 운영 중 70~75% 사용률을 보이고 있어, sys2를 추가하려면 호스트당 하나의 워크로드를 옮기든 새 메모리 증설을 검토하든 결정해야 한다.

Ceph 노드 6대는 분산 스토리지의 최소 권장 단위에 가깝다. Ceph는 3개 monitor가 quorum을 이루므로 최소 3대로도 동작하지만, 6대로 가면 (1) OSD 1개 죽었을 때 rebalance 여유, (2) 향후 Erasure Coding (4+2)으로 전환 가능, (3) replication 분산 효율이라는 세 가지 이점을 얻는다.

### 가상 네트워크 + VLAN

네트워크는 pfSense HA가 게이트웨이가 되어 VLAN 4개를 통제한다. 각 VLAN은 다른 신뢰 수준의 워크로드를 격리하는 목적이다.

| 컴포넌트 | 구성 |
|---|---|
| **pfSense HA** | CARP (VIP 공유) + pfsync (state) + XMLRPC (설정 동기) |
| **VLAN 10** | 172.16.21.0/24 — 용도 확인 필요 |
| **VLAN 20** | 172.16.22.0/24 — DMZ (Edge HAProxy VIP 172.16.22.5) |
| **VLAN 30** | 172.16.23.0/24 DHCP — Internal (K8s 노드, K8s API VIP) |
| **VLAN 40** | 172.16.24.0/24 DHCP — 관리 (bastion) |

VLAN을 4개로 나눈 핵심 이유는 **신뢰 경계의 분리**다. 외부 트래픽이 들어올 수 있는 DMZ (VLAN 20)와 K8s 노드들이 동작하는 Internal (VLAN 30)을 같은 broadcast domain에 두면, DMZ가 침해됐을 때 즉시 내부 노드로 lateral movement가 가능해진다. VLAN으로 분리하고 pfSense가 그 사이의 트래픽을 명시적 룰로 통제하면, 침해 영역을 봉쇄하기 훨씬 쉽다.

```
[Internet]
    │
[라우터 192.168.21.1]
    │
[pfSense HA (Proxmox 위)] ─ CARP ─ [pfSense Backup]
    │ │ │ │
    ▼ ▼ ▼ ▼
  V10 V20 V30 V40
       │   │
       │   ▼ K8s 노드들 + lb-1/lb-2 + MetalLB 172.16.23.50
       │
       ▼ Edge VIP 172.16.22.5 → Edge HAProxy × 2 → K8s Ingress
```

## 🔍 고려한 대안들

### Q1. 가상화 — Proxmox vs 베어메탈 vs VMware vs OpenStack

가상화 플랫폼은 인프라의 가장 기초가 되는 결정이다. 우리가 고민한 옵션은 네 가지였다.

| 대안 | 장점 | 단점 | 적합도 |
|---|---|---|---|
| **베어메탈 K8s** | 가상화 오버헤드 0, 최고 성능 | OS 격리 X, snapshot 어려움 | ★★ |
| **Proxmox (선택)** | KVM 기반 무료, cloud-init 지원, Web UI 풍부 | 5~10% 가상화 오버헤드 | ★★★★★ |
| **VMware vSphere** | 엔터프라이즈 검증, vMotion 등 강력 | 라이선스 비쌈 (학습 부적합) | ★ |
| **OpenStack** | 진짜 클라우드 (multi-tenant, API) | 복잡도 ★★★★★ | ★★ |

베어메탈 K8s를 선택했다면 성능은 최고지만 **VM이라는 격리 단위가 사라진다.** pfSense를 K8s Pod으로 띄울 순 없으니 별도 어플라이언스가 필요해지고, kubelet 자체에 OS 문제가 생기면 노드 전체 재설치다. 우리는 VM 격리 + snapshot + cloud-init이라는 운영 편의를 5~10% 성능 손실보다 더 가치 있게 봤다.

VMware는 가장 검증된 엔터프라이즈 옵션이지만 노드당 연 $1000 수준의 라이선스 비용이 학습 환경엔 부적합하다. OpenStack은 진짜 cloud-like한 multi-tenant 환경을 제공하지만 4명 팀이 운영하기엔 컴포넌트가 너무 많다 (Nova/Neutron/Cinder/Keystone 등 10+ 서비스). **Proxmox는 무료, GUI 풍부, KVM 기반으로 검증된 단순함**이라는 균형을 제공한다.

### Q2. 스토리지 — Ceph 별도 vs K8s 내장 (Rook) vs NFS vs GlusterFS

| 대안 | 장점 | 단점 | 적합도 |
|---|---|---|---|
| **Ceph 별도 (선택)** | 컴퓨트/스토리지 장애 격리, 독립 확장 | 노드 6대 추가, 별도 운영 | ★★★★★ |
| **Rook-Ceph (K8s 내)** | helm install 한 줄 | K8s 장애가 storage로 cascade | ★★★ |
| **NFS** | 단순, 학습 곡선 낮음 | 단일 서버 SPoF, RWO 부적합 | ★★ |
| **GlusterFS** | 분산, 무료 | 2022년 Red Hat EOL 선언 | ★ |

스토리지 결정의 핵심은 **"K8s 클러스터와 같이 죽으면 어떻게 되나"**다. Rook-Ceph는 K8s 안에 Ceph를 깔아 단일 cluster로 통합 관리하는 매력이 있지만, 큰 함정이 있다. K8s API가 죽으면 Rook controller도 못 보고, 그러면 Ceph 상태 진단조차 어려워진다. 즉 **상호 의존성이 cascade로 이어진다**.

우리는 Ceph를 K8s와 물리적으로 분리된 6대 노드 클러스터로 뒀다. K8s가 죽어도 Ceph는 살아있고 (반대도 마찬가지), 각자의 장애를 독립적으로 진단/복구할 수 있다. 운영 부담은 좀 더 들지만 (Ceph 노드 6대 별도 관리), 학습 가치와 안정성이 그만한 가치를 한다.

NFS는 가장 단순하지만 단일 서버 SPoF가 명확하고, K8s의 RWO 요구사항 (대부분 stateful 워크로드)을 잘 못 만족시킨다. GlusterFS는 2022년 Red Hat이 commercial support 종료를 선언해 미래가 불투명해 제외했다.

### Q3. 네트워크 — Spine-Leaf 10G vs 단일 1G

| 대안 | 장점 | 단점 | 적합도 |
|---|---|---|---|
| **Spine-Leaf 10G (선택)** | 확장성, 빠른 replication, ECMP | 스위치 7대 + 광케이블 비용 | ★★★★★ |
| 단일 10G 스위치 | 단순 + 빠름 | 스위치 죽으면 전체 down | ★★★ |
| 1G 단일 스위치 | 가장 저렴 | Ceph replication 1Gbps 병목 | ★ |

네트워크 토폴로지 선택은 Ceph가 강하게 영향을 미친다. Ceph 3-replica 환경에서 1번의 write는 primary OSD가 받아 2개의 secondary OSD로 복제하므로, **네트워크 트래픽이 client write의 약 3배**가 된다. 1G 네트워크 (실효 100MB/s)면 client write throughput이 30MB/s 정도로 제한되고, 노드 1대가 죽어 rebalance가 시작되면 몇 시간씩 걸린다.

10G로 가면 Pod-Pod 통신 실측 5.34 Gbps를 확보하고, Ceph rebalance도 1시간 내로 끝난다. 비용은 단일 1G 스위치 대비 약 ₩450만 더 들지만, 5~10년 사용을 가정하면 합리적인 투자다. 게다가 Spine-Leaf 토폴로지는 노드 추가 시 자동 ECMP로 분산되어 **장기적으로 확장에도 유리**하다.

## 💡 왜 이걸 선택했나

위의 대안 비교를 종합해 우리 결정의 진짜 이유 네 가지를 풀어 설명하면 다음과 같다.

**첫째, 장애 격리(Failure Isolation)가 가장 중요한 원칙이었다.** Ceph가 죽어도 K8s는 살아있고, K8s가 죽어도 Ceph는 살아있다. 이건 단순히 "독립적으로 동작"하는 수준을 넘어, **장애 진단의 본질**에 영향을 준다. 모든 게 같은 cluster 안에 있으면 어디가 진짜 문제인지 추적하기 어렵지만, 분리돼 있으면 "K8s API 응답 OK → Ceph가 문제다" 같은 빠른 격리가 가능하다.

**둘째, 비용 효율을 의식적으로 챙겼다.** VMware 라이선스 노드당 ₩100만/년을 회피하고, OpenStack 운영 인건비도 회피했다. Ceph는 무료고 (Red Hat support는 옵션), Proxmox도 무료다. 같은 인프라를 100% AWS로 옮긴다고 가정하면 월 ₩200만+의 비용이 발생하는데, 우리 온프레는 월 ₩30만 수준 (전기 + 감가)이다.

**셋째, 학습 가치를 명시적으로 평가했다.** Proxmox + Ceph + Spine-Leaf는 모두 AWS/GCP에서도 통용되는 패턴들의 base가 된다. KVM 가상화는 AWS의 Xen/Nitro와 같은 계보고, Ceph S3 호환 RGW는 그대로 AWS S3 SDK가 동작한다. Spine-Leaf 토폴로지는 모든 modern 데이터센터의 표준이다. **여기서 배운 게 다른 환경에도 즉시 적용 가능**하다는 가치가 크다.

**넷째, 성능과 확장성을 미리 확보했다.** 10G 패브릭은 Ceph + K8s + 일반 트래픽이 모두 공존해도 여유가 있다 (실측 5G 정도 사용 중). Spine-Leaf는 노드 추가 시 자동으로 ECMP가 분산해주니, 향후 사이즈가 커져도 네트워크 재설계 없이 확장 가능하다.

## ⚖️ Trade-off

선택의 결과로 얻은 것과 잃은 것을 정리하면 다음과 같다.

| 얻은 것 | 잃은 것 |
|---|---|
| 데이터 주권 (자체 호스팅) | 클라우드 elastic scale 불가 |
| 학습 가치 (전체 stack 이해) | 설치/운영 시간 비용 |
| 비용 ↓ (장기) | 초기 투자금 ↑ (₩1,600만) |
| 장애 격리 (Ceph ↔ K8s) | 노드 추가 (Ceph 6대) |
| 10G 고성능 | 스위치 7대 관리 부담 |

가장 큰 trade-off는 **"제한된 확장성"**이다. 클라우드라면 트래픽이 폭증할 때 즉시 노드를 100대 추가할 수 있지만, 우리는 물리 하드웨어 한계가 있다. 이 약점을 해소하기 위해 AWS 하이브리드 burst 구조를 만든 것이고, 이건 `03-aws-hybrid.md`와 `04-burst-architecture.md`에서 다룬다.

## ⚠️ SPoF + 회복

| SPoF | 영향 | 회복 절차 |
|---|---|---|
| **pfSense MASTER VM 호스트** | CARP 자동 failover (수 초) | 자동 |
| **Spine 스위치 1대** | ECMP 자동 우회 | 자동 |
| **Leaf 스위치 1대** | 그 Leaf 연결된 노드 down | 노드 수동 reboot |
| **Ceph mon 1대** | quorum 유지 (3 중 2) | 노드 회복 |
| **Ceph mon 2대** | quorum loss → write 차단 | 긴급 — mon 1대 살리기 |
| **Proxmox 호스트 1대** | VM 4~5대 down | HA migration 또는 수동 |
| **관리 1G 스위치** | Proxmox UI 접근 X | 콘솔 직접 접근 |

대부분의 단일 컴포넌트 장애는 자동 회복 메커니즘이 있다. pfSense는 CARP로, Spine 스위치는 ECMP로, Ceph는 self-healing으로. 가장 위험한 케이스는 **Ceph mon 2대 동시 죽음**으로, 이 경우 write가 차단되고 즉시 1대라도 살려야 한다. 다행히 mon은 3대가 분산 배치돼 있어 동시 사고 확률은 낮다.

**Proxmox 호스트 1대가 죽는 시나리오는 좀 더 복잡하다.** 그 호스트에 있던 VM들 (보통 4~5대)이 모두 down되는데, pfSense나 K8s CP가 거기 있었다면 영향이 더 커진다. 그래서 pfSense, CP, lb 같은 critical VM들은 **다른 Proxmox 호스트에 분산 배치**해 단일 host 사고가 cluster 전체를 마비시키지 않게 했다.

## 🚀 확장 가능성

여기서부터는 우리 환경이 성장할 때 어떤 옵션이 있는지 설명한다.

### Option A: Ceph 노드 추가 (6 → 9 또는 12)

Ceph는 노드 추가만으로 용량과 IOPS가 동시에 늘어난다. 노드당 ₩50만 (1TB HDD 노드)이라 부담도 크지 않다. 가장 큰 이점은 **EC (Erasure Coding) 4+2 풀이 가능해진다**는 점인데, 이게 활성화되면 같은 raw 디스크로 사용 가능 용량이 33% (3-replica)에서 67% (EC)로 늘어난다. 8대 이상이면 EC가 안정적으로 운영된다.

- 💰 **비용**: 3대 추가 = ₩150만 CapEx + 월 ₩6,000 전기
- 📈 **효율**: Raw 6TB → 9TB, IOPS 1.5배
- 🎯 **추천 시점**: 사용 가능 용량 70% 도달 (현재 ~2TB 중 1.4TB 사용 시)

### Option B: Ceph 노드에 SSD WAL/DB 분리 ⭐ 가성비 최고

BlueStore의 WAL (Write-Ahead Log)와 DB (메타데이터)를 별도 SSD로 분리하는 옵션이다. 노드당 100GB SSD (₩5만 정도)만 추가하면 **seq write 4~8배, randwrite 5~15배 성능 개선**이 가능하다. 우리 현재 측정값이 35 MB/s seq write라 ~150 MB/s 수준까지 올라간다.

투자 대비 효율이 매우 높아 (₩30만으로 성능 ★★★★ 개선), Ceph 디스크 IO가 병목으로 측정되면 즉시 검토할 옵션이다.

- 💰 **비용**: 6대 × ₩5만 = ₩30만 CapEx
- ⏱️ **작업**: 노드별 1~2시간 (offline migration)
- 🎯 **추천 시점**: PVC IO가 병목으로 측정될 때

### Option C: Proxmox 노드 추가

새로운 워크로드 (예: sys2 추가)를 위해 호스트 자원이 부족하면 Proxmox 노드를 늘리는 옵션이다. 노드당 ₩200만+이라 큰 결정이지만, sys2 + 추가 worker + AI/ML 워크로드 같은 진짜 확장이면 합리적이다.

- 💰 **비용**: 2대 추가 = ₩400만 CapEx
- 📈 **효율**: 총 RAM 128GB → 192GB
- 🎯 **추천 시점**: sys1 메모리 압박 + sys2 추가 결정 시

### Option D: 10G → 25G/40G 업그레이드

현재 네트워크 사용률이 5G 정도라 헤드룸이 있지만, 진짜 운영 + 대용량 워크로드 시점엔 더 빠른 네트워크가 필요할 수 있다. 다만 스위치 + NIC 모두 교체라 ₩1500만+ 비용이 들어 학습 환경에선 비추다.

- 🎯 **추천 시점**: 진짜 운영 진입 + 트래픽 ★★★★

### Option E: 다른 사이트로 DR cluster (Ceph multi-site)

지리적 DR을 위해 다른 사이트에 Ceph cluster를 두고 multi-site replication을 설정하는 옵션이다. 진짜 PCI/HIPAA 같은 컴플라이언스 요구가 있을 때나 검토할 만한 큰 작업이다.

### 의사결정 매트릭스

| 신호 | 우선 옵션 |

## ❓ 면접/발표 예상 질문 + 모범 답변

**Q1. 베어메탈에 K8s 안 깔고 굳이 Proxmox 위에 한 이유는?**

A. 네 가지 이유가 있습니다. **첫째, cloud-init으로 노드 추가/교체 자동화**가 가능합니다 — 새 워커 VM을 만들면 자동으로 hostname/SSH key/네트워크가 설정되어 즉시 kubeadm join 가능합니다. **둘째, VM snapshot으로 안전한 실험**이 가능합니다. K8s 1.30에서 1.31 업그레이드 같은 위험한 작업을 snapshot 떠두고 진행할 수 있죠. **셋째, pfSense 같은 어플라이언스 VM을 같은 호스트에 격리해서 띄울 수 있습니다** — 베어메탈이면 pfSense를 위한 별도 하드웨어가 필요합니다. **넷째, 학습 가치** — 가상화와 K8s를 동시에 다뤄볼 수 있죠. 트레이드오프는 5~10% 가상화 오버헤드인데, 우리 워크로드 규모엔 무시 가능한 수준입니다.

**Q2. Ceph를 K8s 안에 Rook으로 했으면 더 단순하지 않았을까요?**

A. 단순함은 ↑이지만 **상호 의존성 cascade가 큰 위험**입니다. Rook-Ceph는 K8s 안에 Ceph operator를 두고 통합 관리하는데, K8s API가 죽으면 Rook controller도 못 봅니다. 그러면 Ceph 상태조차 확인이 어려워지고, 진단이 동시에 마비됩니다. 우리는 Ceph를 별도 클러스터로 두어 ceph-csi-rbd라는 표준 CSI driver를 통해서만 통신하게 했습니다. 이러면 K8s ↔ Ceph 사이 통신이 끊겨도 데이터 자체는 안전하고, 각 cluster의 장애를 독립적으로 진단할 수 있습니다.

**Q3. Spine-Leaf 7대 스위치는 학습 환경엔 과한 것 아닌가요?**

A. 처음 봤을 땐 그렇게 느낄 수 있는데, 자세히 따져보면 합리적입니다. **Ceph replication 트래픽을 격리할 네트워크가 필요**한 게 첫째 이유고, **ECMP로 확장 시 단순하다**는 게 둘째 이유, **DC 표준 토폴로지 학습 가치**가 셋째입니다. 작게 시작하려면 Spine 2 Leaf 2 (4대)도 가능하지만, 이 정도면 학습용으로도 충분히 의미 있는 구조입니다. 비용은 단일 스위치 대비 약 ₩300만 더 드는데, 5년 사용 가정하면 월 ₩5만 정도라 큰 부담은 아닙니다.

**Q4. pfSense를 별도 어플라이언스 아니라 VM으로 한 위험은?**

A. 정확한 지적이고, **솔직히 약점**입니다. Proxmox 호스트가 죽으면 그 위의 pfSense VM도 같이 죽으니 CARP HA 효과가 반감됩니다. 우리가 한 완화 방법은 **pfSense VM 2개를 서로 다른 Proxmox 호스트에 분산 배치**하는 거고, 호스트 부팅 순서/자동 시작도 설정해두었습니다. 진짜 운영 단계에선 별도 어플라이언스로 분리하는 게 정석이지만, 학습 환경에선 자원 효율 + 학습 가치를 우선했습니다.

**Q5. VLAN을 10/20/30/40으로 나눈 이유는?**

A. **신뢰 경계를 명확히 분리하기 위해서**입니다. VLAN 10은 관리/예비, VLAN 20은 DMZ (외부 노출되는 Edge HAProxy), VLAN 30은 Internal (K8s 노드 + lb), VLAN 40은 관리(bastion)입니다. 가장 중요한 분리는 **DMZ ↔ Internal**인데, K8s 노드는 외부에서 직접 안 보이고 반드시 Edge HAProxy를 통과해야 합니다. 만약 DMZ가 침해돼도 Internal로 lateral movement하려면 pfSense 방화벽 룰을 다시 뚫어야 하니, 봉쇄가 쉬워집니다.
